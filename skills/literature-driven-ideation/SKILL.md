# Skill E：基于文献和代码的实验构思

## 概述

本 Skill 从已有实验分析数据中提取瓶颈，定向检索论文和开源代码，生成有数据支撑的
新实验假设，写入对应方向文档和状态表。可在研究过程中的**任何时刻**被调用——
不要求已规划实验全部完成，只要调用者（用户、其他 Skill、或 Auto Research 流程）
认为需要探索新方向即可。

## 输入

由用户主动触发、其他 Skill 级联调用、或 Auto Research 流程调度。传入：
- **目标方向**（可选）：指定某个分支名进行定向构思，或不指定则做跨方向全局构思
- **补充上下文**（可选）：调用者提供的额外信息，如特定瓶颈描述、感兴趣的技术方向等

## 前置条件

- 以下实验分析文档中至少有一份包含有效数据：
  - `Experiment/analysis/experiment-history.md`（实验演进历史与关键发现）
  - `Experiment/experiment_state.md`（实验生命周期状态表）
  - `Experiment/analysis/cross-direction-summary.md`（跨方向对比总结，如存在）
- Agent 具备 WebSearch / WebFetch 能力（Dr. Claw Settings 中已开启）

## 执行步骤

### Step 1：提取当前瓶颈

1. 读取 `Experiment/analysis/experiment-history.md`，提取：
   - **全局最佳结果**及其配置
   - **目标差距**（目标值 - 当前最佳）
   - **瓶颈类别**（per-class 分析中最弱的类别）
   - **已验证有效的改进手段**（从"关键实验发现"章节提取）
   - **已验证无效/有害的手段**（同上）
2. 读取 `Experiment/experiment_state.md` 的"优先级参考"和"建议跳过"，了解当前计划剩余量和已知的低优先级区域。
3. 如有 `Experiment/analysis/cross-direction-summary.md`，读取跨方向对比数据。
4. 如果指定了目标方向，读取该方向的设计文档 `worktrees/<suffix>/docs/[gspo-pinn-]<suffix>/design.md`（其中 `<suffix>` 为分支名去掉 `gspo-pinn-` 前缀，这仅针对当前基于纯GSPO加入PINN的这几个探索方向成立，以后若有新的探索方向则可能不同），理解该方向的算法设计思路和约束。如果未指定方向，跳过此步。

**输出**：结构化瓶颈摘要（内部使用，不写文件），格式：
```
瓶颈摘要：
- 全局最佳: {指标} = {值}, 配置 = {配置}
- 目标差距: {差值}
- 瓶颈维度: {类别/指标/现象}
- 已验证有效: [列表]
- 已验证无效: [列表]
- 未尝试的组合空间: [列表]
```

### Step 2：生成检索查询

基于瓶颈摘要，生成 3-5 个定向检索查询。查询设计原则：

1. **瓶颈驱动**：围绕具体瓶颈（如特定类别分割难度），而非泛泛的任务描述。
2. **方法交叉**：将已验证有效的方法与文献中的新技术组合检索。
3. **时间限定**：优先当前时间向前两年内的工作。

查询模板示例：
| 瓶颈类型 | 查询方向 | 示例查询 |
|----------|---------|---------|
| 特定类别性能差 | 类别均衡 / hard-class | `cardiac MRI myocardium segmentation class-imbalanced 2024 2025` |
| 集成增益不足 | 多样性集成 | `ensemble diversity neural network block selection 2024` |
| 单 seed 强但集成弱 | seed 间策略差异化 | `diverse policy ensemble reinforcement learning vision 2025` |
| 架构本身的上限 | SOTA 方法对比 | `ACDC cardiac segmentation state-of-the-art leaderboard 2025 2026` |
| 已有方法的未探索组合 | 组合优化 | `top-k subset selection critic network adaptive reward 2024` |

### Step 3：执行检索并筛选

对每个查询：

1. **论文检索**：WebSearch arXiv、Google Scholar、PapersWithCode。
2. **初步筛选**（每个查询取 top 5-8 篇）：
   - 排除与任务不相关的论文
   - 排除与已验证无效手段重复的思路
   - 优先有代码开源的工作
3. **深度阅读**（筛选后取 top 2-3 篇/查询）：
   - WebFetch 获取 arXiv PDF 摘要 + 方法章节
   - 提取核心思路、关键公式/模块、报告的指标提升

4. **写入参考文献文档**：将所有通过筛选的论文条目追加到 `Survey/references/literature-survey-log.md`，每条包含：

```
### {title} ({year})
- **arXiv**: {链接}
- **核心思路**: {一句话}
- **与当前系统的关联**: {具体哪个瓶颈}
- **可复用模块**: {具体描述}
- **代码**: {GitHub 链接或无}
- **检索日期**: {YYYY-MM-DD}
- **检索查询**: {触发本条结果的查询}
```

如果 `Survey/references/literature-survey-log.md` 不存在，创建并添加文件头说明。该文档作为所有 Skill E 调用的累积参考文献库，避免重复检索。

### Step 4：开源代码分析（有代码的论文）

对有 GitHub 仓库的候选论文：

1. **不要 Clone 整个仓库**。用 WebFetch 直接读取关键文件（模型定义、损失函数、训练配置）。
2. **差异分析**：对比候选方法的核心思路与本项目的整体架构和已有模块，重点关注：
   - 候选方法引入了哪些本项目中没有的机制或模块？
   - 候选方法在与本项目相似的问题上（如块选择、损失设计、特征适配、集成策略等）采用了什么不同的解法？
   - 不要局限于逐文件对比——如果候选方法提出了一种全新的思路（如新的训练范式、新的数据增强策略、新的评估方法等），同样应该纳入考虑。
3. **可行性判断**：
   - 候选模块或思路是否可以嫁接到本项目架构？需要什么级别的改动？
   - 是否与已验证有效的手段兼容？

### Step 5：生成可测试假设

将 Step 3-4 的发现转化为假设。每个假设必须包含：

```
### 假设 H{N}: {一句话描述}

**来源**: {论文标题} ({arXiv 链接})
**瓶颈对应**: {解决哪个瓶颈}
**核心思路**: {2-3 句描述要做什么修改}
**预期效果**: {定量预期，如 "MYO dice +0.005~0.01"}
**预期风险**: {可能的副作用}
**实现复杂度**: {低/中/高} — {需要改哪些文件，估算行数}
**与现有有效手段的兼容性**: {是否可叠加在当前最佳配置上}
**建议基础配置**: {在哪个现有最佳配置基础上做}
```

**过滤规则**：
- 假设必须与至少一个已验证有效的手段兼容，否则标注风险。
- 假设不能重复已验证无效的思路（如直接加 PINN 损失约束）。
- 实现复杂度"高"的假设最多保留 1 个，优先出"低"和"中"的。

### Step 6：用户审批门

**暂停执行**，向用户展示所有假设，格式：

```
## 文献驱动的新实验方案

### 瓶颈分析摘要
{Step 1 输出}

### 检索到的关键论文
{Step 3 输出精简版，每篇 1-2 行}

### 候选假设（按推荐优先级排序）

1. H1: {标题} — 预期 {效果}, 复杂度 {低/中/高}
2. H2: ...
3. H3: ...

### 推荐方案
建议先执行 H{X} 和 H{Y}，理由：{...}

请确认：
- [ ] 同意全部
- [ ] 只执行 H{X}
- [ ] 需要修改某个假设
- [ ] 全部拒绝，手动指定方向
```

**等待用户回复**。如果是 Auto Research 模式（无人值守），则默认执行推荐方案中优先级最高的 2 个假设。

### Step 7：写入计划文档

对用户批准的每个假设：

1. **确定目标分支**：
   - 如果假设属于已有方向 -> 写入对应 worktree 的 `experiment-plan.md`
   - 如果是全新方向 -> 创建新分支 + worktree + 文档结构（按 `branches.md` 的约定）
2. **更新 `experiment-plan.md`**：添加新的实验条目，含命令行模板。
3. **更新 `experiment_state.md`**：在对应方向表格中添加新行，状态全 `—`。
4. **更新 `branches.md`**：如果新建了分支。
5. **更新 `experiment-history.md`**：在"关键实验发现"中添加文献来源说明。
6. **Git 提交** + 更新 `changelogs.md`（遵循现有 Version Control 规则）。

### Step 8：报告完成，交还控制权

本 Skill 在写入计划文档后**不自动调用 Skill A**。是否启动实验由调用者决定：
- 如果是用户直接调用，询问用户是否要立即启动实验（调用 Skill A）。
- 如果是其他 Skill 级联调用（如 Skill C），由上级 Skill 决定后续动作。
- 如果是 Auto Research 模式，由 Auto Research 流程决定是否继续。

## 输出格式

```
## 文献驱动构思报告

### 瓶颈分析
- 全局最佳: {指标}
- 目标差距: {差值}
- 核心瓶颈: {描述}

### 检索覆盖
- 查询数: {N}
- 论文阅读: {M} 篇
- 代码分析: {K} 个仓库
- 参考文献已写入: Survey/references/literature-survey-log.md

### 生成假设
- 总数: {J}
- 用户批准: {P}
- 写入计划: {P} 条新实验

### 新增实验
- {方向}/{计划项}: {EXP 模板} — 状态 —/—/—
  来源: {论文}

### 后续动作: 计划已写入，待调用者决定是否启动实验
```

## 约束

- **每个假设必须有论文或代码引用支撑**。禁止纯推测性的"不如试试 X"。
- **不重复已验证无效的思路**。在生成假设前必须检查 experiment-history.md 的"已验证无效"列表。
- **实现建议必须具体到文件和函数名**。不能说"修改模型架构"，要说"在 `sam2_seg.py:UPerHead.forward()` 中加入 X 模块"。
- **兼容性检查必须显式**。每个假设必须说明能否叠加在当前最佳配置上。
- **单次调用生成假设不超过 5 个**。宁可精准少量，不要泛泛多量。
- **检索论文如无法验证真实性，必须标注 `[未验证]`**。Agent 不得编造不存在的论文。
